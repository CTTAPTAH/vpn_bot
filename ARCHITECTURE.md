# Архитектура проекта VPN Bot

## Общая идея

Проект построен по принципам Clean Architecture с разделением на слои.

Цель архитектуры:
- Изолировать бизнес-логику
- Упростить тестирование
- Позволить менять БД и внешние сервисы без переписывания логики
- Разделить ответственность между слоями


---

# Структура слоёв

Проект разделён на следующие уровни:

presentation → application → domain  
application → infrastructure


## 1. Domain (Предметная область)

Содержит бизнес-сущности и правила системы.

Примеры:
- User
- Plan
- Subscription
- Payment

В этом слое:
- Нет SQLAlchemy
- Нет Telegram
- Нет работы с БД
- Нет внешних API

Domain — это чистая бизнес-логика.


## 2. Application (Сценарии использования)

Содержит use cases — конкретные действия системы.

Примеры:
- Покупка подписки
- Продление доступа
- Получение VPN-ключа

Application:
- Использует Domain
- Работает через интерфейсы (UoW, репозитории, VPN gateway)
- Управляет транзакциями

Application не зависит от конкретной реализации БД.


## 3. Infrastructure (Инфраструктура)

Содержит техническую реализацию:

- SQLAlchemy модели
- Репозитории
- Реализацию Unit of Work
- Клиент XUI

Infrastructure зависит от:
- Application (интерфейсы)
- Domain

Этот слой отвечает на вопрос:
«Как именно это реализовано технически?»


## 4. Presentation (Интерфейс)

Отвечает за взаимодействие с пользователем (Telegram).

Задачи:
- Принимать сообщения и callback-и
- Вызывать use cases из application
- Формировать ответы

В этом слое не должно быть бизнес-логики.


## 5. Core

Содержит:
- Конфигурацию
- Общие утилиты
- Константы

Это вспомогательный слой.


## 6. App (Точка входа)

Место, где:
- Создаются зависимости
- Инициализируются сервисы
- Запускается бот

Это bootstrap приложения.


---

# Направление зависимостей

Зависимости направлены внутрь:

Infrastructure → Application → Domain  
Presentation → Application  

Domain ни от кого не зависит.


---

# Правила разработки

1. Бизнес-логика должна находиться только в domain.
2. Application не должен импортировать SQLAlchemy.
3. Presentation не должен работать напрямую с БД.
4. Infrastructure не должен содержать бизнес-правил.
5. Все взаимодействия с БД происходят через Unit of Work.


---

# Зачем это нужно?

Такая архитектура позволяет:

- Легко тестировать бизнес-логику
- Заменить БД без изменения логики
- Заменить Telegram на другой интерфейс
- Поддерживать проект при росте сложности


---

# Ключевая идея

Telegram-бот — это лишь интерфейс.

Основная ценность проекта — бизнес-логика управления VPN-доступом.
